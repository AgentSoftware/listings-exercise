# Notes

Buyers can save a search, view and delete their saved searches, and see alerts
for new listings that match. Alerts are generated by a nightly command
(`alerts:dispatch`) and delivered as one digest per buyer per run.

## The decision everything else follows from

Support's *"please don't spam people"* is the design driver, and it separates two
things that look like one:

- **The alert record** — a durable "this property matched your search", one per
  listing, so the alerts page can list properties individually.
- **The notification** — the thing that actually interrupts someone. Batched.

Deduplicating per listing only stops the *same* listing alerting twice; twenty
listings going live across a Tuesday would still be twenty interruptions. So
alerts come from a **scheduled run**, not an event fired when a listing goes
live, and one run sends one email per buyer covering everything it found.

That removed machinery rather than adding it: no `ListingWentLive` event, no
listener, no publish action, no observer — the run derives "went live" from
`status` and `listed_at`. It also buys a behaviour an event can't have: a listing
that goes live and sells before the evening run is never in the result set, so we
don't advertise a property that's already gone.

**The cost is latency** — up to a day. For most searches a digest of six houses
reads better than six pings, but someone hunting in a hot market wants it sooner.
The answer isn't a faster cron, it's per-search frequency (instant / daily /
weekly), with "instant" going back to an event-driven path for buyers who opt in.
That's what I'd build next.

## Other decisions

**Idempotent by state, not by time.** The run selects listings with *no alert row
yet* (`NOT EXISTS`), not "added in the last 24 hours". A time window is fragile —
one failed run and those listings are lost silently, which nobody notices until a
buyer asks why they never heard about a house. Selecting on absence means a
missed day is caught up by the next run, and re-running by hand is always safe.
The seven-day window only bounds the scan; it's the recovery budget, not the
correctness mechanism.

**Duplicate alerts: one, not two.** A listing matching two of your searches is
still one property. That's a unique index on `alerts (user_id, listing_id)`, so
it's the database's guarantee, not a rule the writing code has to remember. The
oldest matching search is credited, so attribution is stable between runs.

**Backfill: no.** A saved search alerts on listings that go live from then on.
Backfilling would dump thirty alerts on someone the moment they save a broad
search — exactly the complaint Support raised. Instead the saved-searches page
links each search to the browse results for its criteria, so "what matches right
now" is one click away in a UI that already exists. That made the policy one
clause of one query rather than a special case.

**Criteria live in one value object.** Three places must agree on what "matches"
means: the browse filters, the saved-search form, and the alert run.
`App\Search\ListingCriteria` holds the rule once, as a query (`applyTo`), a
predicate (`matches`) and validation rules; `SavedSearch::matching()` is the same
rule inverted. Three implementations of one rule is the real risk this feature
carries, so the tests assert directly that they select the same listings across a
grid of boundary values rather than trusting the inversion by eye.

**Criteria are columns, not JSON** — the run matches in SQL, which needs real
columns, and it keeps the values typed. Cost: a migration per new criterion.

**Which criteria.** The same four the browse page has. A price *range* is
probably better than a max, but a saved search should be expressible as a browse
search, so I'd add `min_price` to both at once or neither. What I'd add first is
a location filter finer than region — "Leeds" is a big place to be alerted about.

**Ownership is structural.** These records are only reached via
`$user->savedSearches()` / `$user->alerts()`, and `destroy` resolves through the
relationship rather than route-model binding, so another buyer's record is a 404
by construction. Hence no policy: there's no unscoped query to protect.

## Where it wouldn't hold up

- **Volume.** One inverted query per new listing is fine at a few dozen a day; a
  bulk import of 10,000 is 10,000 queries in one long command. Then you'd batch
  by region and fan out to queued jobs, or move to a set-based join. I didn't
  write the clever join first — the loop is easier to read and test.
- **Cost grows with saved searches, not listings.** The inverted query indexes
  poorly because every criterion is `IS NULL OR …`; at scale you'd bucket by
  region first.
- **The unread count runs on every page load**, including pages that don't use it.
- **`(user_id, listing_id)` unique forever** means a property withdrawn and
  re-listed a year later never alerts again. Probably right; arguably wrong.
- **No cap on a digest's alert rows** — it names five and summarises the rest.

## Left out deliberately

Real email (`MAIL_MAILER=log` renders the digest so you can read it); front-end
tests, so the Vue is covered only through the props its pages receive; editing a
saved search; pausing one instead of deleting it.

## On working with AI

Built with Claude Code, reviewed and directed by me. Two things worth flagging as
the sort of thing that gets missed: a fixture left `property_type` random, so
`SavedSearchTest` passed alone but failed intermittently in the full suite; and
the unread badge silently vanished on the alerts page because a page prop named
`alerts` overrides a shared prop of the same name. I found the second by driving
the running app, not from the tests — it's now a top-level scalar with a
regression test across all three pages.
